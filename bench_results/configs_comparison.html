Understanding LLM serving — latency, throughput & memory

Serving a large language model is a balancing act between three things: how fast each user gets an answer (latency), how many users you can serve at once (throughput), and how much GPU memory the whole thing needs. This page explains what those mean from scratch, then runs three real experiments on vLLM to show how a handful of server settings move them around.

First: what happens when a model answers

When you send a prompt, the server does the work in two distinct phases:

Phase 1 · Prefill

The model reads your whole prompt in a single pass and produces the first token. This is compute-heavy but parallel, and it is what you wait through before anything appears.

Phase 2 · Decode

The model then generates the rest one token at a time, each step reading everything written so far. These tokens stream out; the gap between them is what makes text feel fast or sluggish.

That timeline gives us the two latency numbers used throughout this page, plus the two throughput and memory numbers that describe the server as a whole:

TTFT — time to first token
The prefill wait (plus any time spent queued). This is the lag a user feels before the answer starts. We track its typical value (p50) and its near-worst-case tail (p99) — the tail is what makes a service feel unreliable even when the average looks fine.
ITL — inter-token latency
The decode gap between streamed tokens. Low ITL is a smooth, fast-flowing response.
Throughput — tokens/sec & requests/sec
How much work the whole server gets done: total tokens emitted per second across every user at once. This is what you are paying the GPU for, and it usually rises with more simultaneous users — up to a point.
Offered load — requests/sec
How much traffic is arriving. Every chart sweeps this along the bottom, from light to overloaded, so you can see where a setting stops coping.
The KV-cache — the memory that inference actually spends
During decode, the model would have to re-read the entire sequence for every new token. Instead it caches each token's attention state (its "keys" and "values") in GPU memory — the KV-cache — so each new token only looks at the cache. That cache grows with every token of every in-flight request, so more users and longer contexts cost more memory. It lives in the GPU alongside the model weights, and when it fills, the server must preempt — evict a running request and redo it later — which spikes latency. Fitting more into it is the whole point of the memory experiments below.
The core tension

Running more requests together fills the GPU and lifts throughput — but makes every user's tokens wait for the batch, and eats KV-cache memory. Push too hard and requests queue (latency explodes) or the cache overflows (preemptions). Tuning a server is finding the point just before that edge. The three experiments below each turn one knob and watch where the edge is.

The test rig

Every number on this page comes from one small language model (Qwen2.5-0.5B, a 0.5-billion-parameter model, AWQ-quantized) served by vLLM on a 4 GB laptop GPU (an RTX 3050 under WSL2). A tiny model on a tiny card is deliberate: the effects below are the same ones you meet on an 80 GB datacentre GPU, just at a scale you can run at home. To drive traffic we use GuideLLM, which fires synthetic requests at a fixed rate and measures what comes back.

The single most important idea for reading the charts: we sweep the offered load — the number of requests arriving per second, along the bottom of every chart — from gentle (1/s) to overloaded (12/s). A server can look perfect until traffic rises, so we watch how each setting behaves as the pressure climbs. Every configuration is driven with the exact same requests, so the lines are directly comparable.

Experiment 1 — Batching: trading latency for throughput

the knob: --max-num-seqs

A GPU is far more efficient when it works on many sequences at once. vLLM does this with continuous batching: on every decode step it advances a whole batch of in-flight requests together, filling the GPU. The flag --max-num-seqs caps how many requests may run in that batch at one time.

A bigger cap means more tokens computed per GPU step, so higher total throughput. But each step also gets heavier — every user waits for the whole batch to advance — and if the cap is too small, arriving requests pile up in a queue instead of being served. That is why this single number pushes latency and throughput in opposite directions. It is the first knob to reach for.

The exact commands we compared

Everything else is identical — only the highlighted flag changes between runs.

seqs-4 — max-num-seqs = 4
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.6 \
  --max-num-seqs 4
seqs-32 — max-num-seqs = 32
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.6 \
  --max-num-seqs 32
seqs-128 — max-num-seqs = 128
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.6 \
  --max-num-seqs 128

What the run showed

What we learned

There is no single best setting. max-num-seqs=4 starves under load — up to 192 requests queue and the first-token wait blows past 13.7 seconds. max-num-seqs=128 swings the other way: it accepts so much work that the little GPU thrashes and throughput collapses from 1422 to 169 tok/s at the heaviest load. seqs-32 is the sweet spot, sustaining the most work (1874 tok/s) without falling over.

Experiment 2 — Memory: how much room the KV-cache gets

the knob: --gpu-memory-utilization

After the model weights are loaded, whatever GPU memory is left becomes the KV-cache pool — the scratch space that holds every in-flight request's attention state (see the primer above). --gpu-memory-utilization sets the fraction of the card vLLM is allowed to claim; a bigger fraction leaves more room for the KV-cache, so more requests (or longer prompts) can run before it fills.

If the KV-cache fills, vLLM must preempt — evict a running request and recompute it later — which spikes latency and drops throughput. So the question is: on this hardware and workload, does a tighter memory budget actually hurt, or is something else the limit first?

The exact commands we compared

Everything else is identical — only the highlighted flag changes between runs.

seqs-128 — max-num-seqs = 128
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.6 \
  --max-num-seqs 128
mem-0.45 — gpu-mem-util = 0.45
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.45 \
  --max-num-seqs 128

What the run showed

seqs-128 max-num-seqs = 128mem-0.45 gpu-mem-util = 0.45
What we learned

Cutting the budget from 0.60 to 0.45 did push peak cache use up (39% → 70% of budget), but it never filled: zero preemptions, and throughput barely moved (1422 ≈ 1435 tok/s). The lesson: on this GPU the bottleneck is compute, not memory — the chip runs out of speed long before the cache runs out of room. Memory tuning only pays off once you are actually memory-bound.

Experiment 3 — Quantization: the same cache in half the bytes

the knob: --kv-cache-dtype fp8

Every token in the KV-cache is normally stored as 16-bit numbers. KV-cache quantization stores them as 8-bit floats instead (--kv-cache-dtype fp8), halving the bytes per token for a tiny, usually invisible, accuracy cost.

Half the bytes per token means roughly twice the effective KV-cache — you can hold twice the concurrency or twice the context in the same memory budget. Here we hold the budget fixed at the tight 0.45 setting and switch fp8 on, to isolate exactly what it buys.

The exact commands we compared

Everything else is identical — only the highlighted flag changes between runs.

mem-0.45 — gpu-mem-util = 0.45
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.45 \
  --max-num-seqs 128 \
  # (no --kv-cache-dtype flag: defaults to 16-bit)
fp8-0.45 — fp8 KV @ 0.45
VLLM_USE_V2_MODEL_RUNNER=0 vllm serve Qwen/Qwen2.5-0.5B-Instruct-AWQ \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.45 \
  --max-num-seqs 128 \
  --kv-cache-dtype fp8

What the run showed

mem-0.45 gpu-mem-util = 0.45fp8-0.45 fp8 KV @ 0.45
What we learned

At the same 0.45 budget and the same load (8 req/s), fp8 held the same work in 52% of the memory (45% → 24% of budget) with no throughput penalty (1347 vs 1928 tok/s at that load — the gap is within single-run noise). That freed space is headroom you would spend on longer prompts or more concurrent users — it just doesn't help here, because (see Experiment 2) memory was never what held us back.

Putting it together — how to actually tune a server

The three experiments give a simple recipe, in order:

  1. Start with the batch cap (--max-num-seqs). It is the biggest lever on both latency and throughput. Too small and requests queue until the first-token wait becomes seconds; too large and a small GPU thrashes and throughput collapses. Find the largest cap that still holds your latency target under peak load.
  2. Decide what "good" means with a latency budget (an SLO). Pick a ceiling for the p99 first-token wait — say 500 ms — and read across each throughput chart to the busiest point still under that ceiling. That, not the raw peak, is your usable throughput.
  3. Only tune memory once you are memory-bound. If you never see preemptions and cache use stays well under 100% (as here), more memory won't help — you are compute-bound, so buy compute or pick a smaller model. When you do see preemptions, raise --gpu-memory-utilization or turn on --kv-cache-dtype fp8 to roughly double the cache for free.

Which knob dominates depends on your model, GPU and traffic — the value of a page like this is that it shows you how to find out, not a universal answer.

Caveats. Each configuration was measured once (n = 1), so treat small differences — a few percent of throughput — as noise; the large effects (a batch starving, a batch collapsing, fp8 halving the cache) are real. Results are specific to this model, this 4 GB GPU and this short-prompt workload. KV-cache, queue depth and preemptions are read from vLLM's own /metrics endpoint while the load runs.
